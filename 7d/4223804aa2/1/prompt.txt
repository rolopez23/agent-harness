## Detailed Technical Breakdown: andrej-karpathy-skills

### 1. **What It Does**

This repository encodes **Andrej Karpathy's coding philosophy for LLM-assisted development** — addressing four specific pitfalls he identified in how AI models approach coding tasks:

- Making unfounded assumptions without verification
- Over-engineering solutions with unnecessary abstractions
- Silently proceeding with ambiguity instead of asking clarifying questions
- Refactoring unrelated code instead of making surgical changes

The project packages these insights into **behavioral guidelines** (not style rules) that influence how Claude/Cursor agents approach coding work. This is primarily about **CODING PRACTICES and DECISION-MAKING APPROACH**, not about tone or personality.

### 4. **Content — The Four Core Principles**

Here are the actual behavioral standards encoded:

#### **Principle 1: Think Before Coding**

&gt; "Don't assume. Don't hide confusion. Surface tradeoffs."

Core practice:
- State your assumptions explicitly
- If uncertain, ask clarifying questions before implementing
- Present multiple interpretations when ambiguity exists
- Acknowledge simpler alternatives upfront

**Example anti-pattern:** When asked to "export user data," an LLM typically assumes all users without questioning privacy implications, file location, or field selection. Instead: ask scope, format, field selection, volume considerations upfront.

#### **Principle 2: Simplicity First**

&gt; "Minimum code that solves the problem. Nothing speculative."

Core practice:
- Avoid speculative features (things not in the requirement)
- Don't add unnecessary abstractions or design patterns prematurely
- Don't implement unasked-for flexibility or error handling for improbable scenarios
- If substantial code reduction is possible through refactoring, do it; otherwise leave it

**Example anti-pattern:** A request to "calculate discount" doesn't need abstract base classes, strategy patterns, or configuration dataclasses. Start simple:
```python
def calculate_discount(amount: float, percent: float) -&gt; float:
    return amount * (1 - percent / 100)
```
Only refactor when actual requirements demand it.

#### **Principle 3: Surgical Changes**

&gt; "Touch only what you must. Clean up only your own mess."

Core practice:
- Don't "improve" adjacent code, comments, or formatting
- Match existing style, even if you'd do it differently
- Remove only code your changes have made obsolete (imports, variables)
- Do NOT remove pre-existing dead code unrelated to your change
- Don't refactor while fixing bugs; fix first, refactor separately

**Example anti-pattern:** When fixing "empty emails crash the validator," resist the urge to reformat quotes, add type hints, or rewrite docstrings. Change only the specific lines addressing that bug.

#### **Principle 4: Goal-Driven Execution**

&gt; "Convert abstract tasks into verifiable success criteria with specific checkpoints."

Core practice:
- Transform vague goals like "make it work" into measurable criteria
- Write tests that fail, then make them pass
- Create brief multi-step plans with verification checkpoints at each stage
- Break multi-step work into independently testable stages

**Example:** Rather than vague plan "review and improve code," specify:
1. Write test reproducing the bug
2. Implement fix
3. Verify test passes
4. Confirm no regressions

### 3. **Hook Mechanism — How Tone Injection Works**

Caveman uses **three Claude Code lifecycle hooks** that wire into `~/.claude/settings.json`:

#### **Hook 1: `caveman-activate.js` (SessionStart)**
**When:** Fires at the beginning of every Claude Code session
**What it does:**
1. Reads current mode from flag file at `~/.claude/.caveman-active`
2. Fetches the authoritative ruleset from `skills/caveman/SKILL.md` (or hardcoded fallback)
3. **Filters ruleset by intensity level** (lite/full/ultra/wenyan variant)
4. Injects filtered rules as **system context** to the model on every turn

**Code flow (simplified):**
```javascript
// From caveman-activate.js
const mode = readFlag(flagPath); // reads ~/.claude/.caveman-active
const ruleset = loadRuleset(); // reads SKILL.md or uses fallback
const filtered = filterByLevel(ruleset, mode); // e.g., full mode strips articles
// Then emits context to Claude's SessionStart hook
```

**Safety hardening:**
- Symlink-safe flag reading (O_NOFOLLOW flag)
- File size cap (64 bytes) to prevent exfiltration
- Silent fail on all filesystem errors (never blocks session)
- VALID_MODES whitelist prevents injection

#### **Hook 2: `caveman-mode-tracker.js` (UserPromptSubmit)**
**When:** Fires after user submits every prompt
**What it does:**
1. Parses user input with regex patterns to detect activation/deactivation commands
2. Recognizes both slash commands (`/caveman lite`, `/caveman-commit`) and natural language ("activate caveman", "be brief")
3. **Updates mode state** by writing to `~/.claude/.caveman-active` flag file
4. For one-shot commands (`/caveman-commit`), **saves previous mode**, executes one-shot, then **restores previous mode**

**Activation patterns matched:**
```regex
/caveman\s*(lite|full|ultra|wenyan.*)?
activate caveman
be brief
less tokens
talk like caveman
// ... and ~20 more natural language patterns
```

**Deactivation patterns:**
```regex
stop caveman
normal mode
disable caveman
turn off caveman
```

**State machine:**
- Prose modes (lite/full/ultra/wenyan) persist across turns
- Independent modes (commit/review/compress) are one-shot with auto-restore
- Per-turn reinforcement emits mode reminder to prevent model drift when multiple plugins compete for attention

#### **Hook 3: `caveman-statusline.sh` (statusline badge)**
**When:** Renders in Claude Code's statusline continuously
**What it displays:**
- `[CAVEMAN]` in orange (ANSI color code 172) if mode is "full"
- `[CAVEMAN:LITE]`, `[CAVEMAN:ULTRA]`, etc. for other modes
- Optional suffix with lifetime token savings (e.g., `[CAVEMAN] -65%`)

**Security hardening:**
- Refuses symlinks
- Strips control characters (blocks terminal-escape injection)
- Validates against whitelist of recognized modes
- Reads pre-rendered stats file to avoid expensive subprocess calls per keystroke

#### **Configuration in settings.json**
The installer modifies `~/.claude/settings.json` to wire these hooks:

```json
{
  "hooks": {
    "SessionStart": [
      {
        "command": "node ~/.claude/hooks/caveman-activate.js",
        "runMode": "terminal"
      }
    ],
    "UserPromptSubmit": [
      {
        "command": "node ~/.claude/hooks/caveman-mode-tracker.js",
        "runMode": "terminal"
      }
    ]
  },
  "statusline": {
    "left": ["~/.claude/hooks/caveman-statusline.sh"],
    "right": []
  }
}
```

  - /caveman

  - normal mode
  - disable caveman

  lite:  Drop filler/hedging but keep articles and full sentences
  full:  Articles gone, fragments allowed, short synonyms [DEFAULT]
  ultra: Strip conjunctions when meaning stays clear; one word when sufficient
  
  wenyan-lite:   Classical Chinese compression (lite intensity)
  wenyan-full:   Classical Chinese compression (full intensity)
  wenyan-ultra:  Classical Chinese compression (ultra intensity)

# Auto-Clarity Exception:
  Revert to normal speech for:
  - Security warnings
  - Irreversible action confirmations
  - Multi-step sequences where fragment order risks misread
  
  Resume caveman after clarification.

# DO NOT apply caveman to:
  - Code blocks (keep exact)
  - Commit messages (normal prose)
  - Pull requests (normal prose)
  - Technical terms &amp; exact API names (keep verbatim)
  - Acronyms (DB/API/HTTP stay as-is)

### 6. **Installation Process — What Gets Configured**

The installer (`bin/install.js`) is a **unified Node.js script** that:

1. **Detects all installed agents** on your system:
   - Scans PATH for binaries (claude, cursor, cline)
   - Checks IDE extension directories (.vscode/extensions, .cursor/extensions)
   - Scans JetBrains plugin caches
   - Checks macOS application bundles
   - Checks Linux/Windows configuration directories

2. **Installs per-platform:**

   **For Claude Code (Tier 1 — Full auto-activation):**
   - Runs `claude plugin install caveman` (native plugin marketplace integration)
   - Copies hook files to `~/.claude/hooks/`:

     - `package.json` (hook dependencies)
   - Modifies `~/.claude/settings.json` to wire SessionStart, UserPromptSubmit, and statusline hooks
   - **Integrity check:** Downloads hooks from pinned release, validates SHA-256 against manifest
   - Backs up existing settings.json before modification
   - Uses Node.js stdlib for safe JSON merging (handles JSONC comments)

   - Delegates to `npx skills add` upstream ecosystem

   - Zero external npm dependencies (uses Node.js stdlib only)

   - Dry-run mode: `--dry-run` previews changes without executing
   - Graceful degradation: falls back to npx-skills if native installs unavailable
   - Silent fail: filesystem errors don't block session start

### 7. **Coding-Standards Injection — Does It Affect Code Writing?**

**Short answer:** NO. Caveman is **output-tone only**. It does NOT:
- Inject code style guidelines before code is written
- Modify coding standards or linter rules
- Change the model's code generation patterns
- Add pre-commit hooks or AST transforms

**What it DOES:**
- Applies tone transformation to the **assistant's explanatory text**
- Leaves code blocks, commits, and PRs in **normal prose** (untouched)
- Preserves all technical terms, error messages, and command outputs exactly
- Never modifies the user's prompts

**Example:**
```
User: "Write a function to validate emails"

Before caveman:
"Sure! I'd be happy to help. Here's a function that validates email addresses 
using a regular expression..."
[code block - unchanged]

After caveman:
"Email validator:"
[code block - unchanged]
```

The code output is identical; only the narration is compressed.

### 7. **Coding-Standards Injection — Pre-Code vs. Post-Code**

Ponytail injects instructions **BEFORE code generation** — not post-processing:

**Injection Point**: System prompt / LLM context before the model generates code

**Mechanism**: The ladder is presented *as part of the system message*, so the model evaluates necessity, reuse, and alternatives **before** writing a single line.

**NOT applied post-generation**: No linter, no rewriting pass. The instruction shapes decision-making during generation.

**Marked Code**: Shortcuts/known limitations are marked with `ponytail:` comments in the generated code itself:
```python
# ponytail: O(n²) scan but dataset &lt; 1000 rows, safe for now
# upgrade path: add index if performance needed
```

### 8. **Safety Guarantees** (Non-Negotiable)

The plugin **never optimizes away**:
- **Trust boundary validation**: Input validation at system/user boundaries
- **Data loss prevention**: Error handling that prevents data loss
- **Security practices**: No weakening of crypto, auth, or trust checks
- **Accessibility standards**: WCAG compliance never sacrificed
- **Explicitly requested features**: If the user asked for it, the ladder doesn't apply

These are **invariant phrases** checked by the `check-rule-copies.js` validation script to prevent accidental regression.

### 11. **Architecture Patterns to Build Similar**

If you're building something similar:

1. **Canonicalize rules in one file** (AGENTS.md) + validation script to keep copies in sync
2. **Support multiple hook mechanisms**:
   - System prompt transformation (most universal)
   - Pre-LLM-call hooks (if platform supports)
   - MCP server (for agents without plugin hooks)
   - Editor rules files (for IDE integration)
3. **Implement mode-switching** (lite/full/ultra/off) with persistent state
4. **Protect safety invariants** via phrase-checking in tests/CI
5. **Provide slash commands** for runtime control (mode switching, auditing)
6. **Mark intentional optimizations** in code comments (upgrade paths)
7. **Benchmark real agent sessions** (not single-shot LLM calls) to validate claims
